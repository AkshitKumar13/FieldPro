1. Executive Summary

FieldPro is a cross-platform .NET MAUI field-service application. The current POC provides a login experience, a dashboard, work-order data, and logout behavior. Authentication is implemented locally for the POC using Entity Framework Core with SQLite and secure device storage.

Implemented

  • MAUI UI with Shell navigation.
  • Login and logout workflow.
  • EF Core SQLite user store.
  • PBKDF2 password hashing with per-user salt.
  • SecureStorage-backed authenticated user ID.
  • SQLite work-order persistence and seed data.

POC Boundaries

  • Authentication is device-local, not server-backed.
  • One development user is seeded from JSON.
  • No registration, password reset, roles, refresh tokens, or remote API yet.
  • Work orders currently use the existing sqlite-net data layer.

2. POC Goals

GoalResult
Prove a real login flowCredentials are verified against an EF Core user record instead of a hard-coded conditional.
Keep passwords out of the database in plain textPasswords are transformed with PBKDF2-SHA256, 100,000 iterations, a random 16-byte salt, and a 32-byte derived key.
Keep the session across app navigationThe authenticated user ID is stored in platform-backed MAUI SecureStorage.
Provide reliable logoutLogout removes the secure user ID and clears the in-memory application session.

→
2. QueryAuthService loads active EF user

3. VerifyPBKDF2 hash comparison

5. SessionMark AppSession authenticated

Logout Flow

Shell resolves IAuthService, removes the SecureStorage user ID, clears IAppSession, and navigates to the login route with a cleared stack.

5. Data and Security Design

Auth database

EF Core uses a dedicated SQLite file named fieldpro-auth.db3. The User entity contains an ID, unique email, password hash, password salt, and active flag.

Work-order database

The existing sqlite-net database remains separate from authentication. This limits schema coupling while the POC is being developed.

ConcernCurrent POC treatmentProduction evolution
Credential seedauth-seed.json is packaged for initial local setup only.Remove default credentials from the client and provision accounts through an identity service.

Important: The credentials in auth-seed.json are development credentials. They must not be shipped unchanged in a production release.

6. POC Acceptance Criteria

  • First launch creates the auth SQLite database and seeds a user from JSON when no users exist.
  • Valid credentials navigate to the dashboard.
  • Invalid credentials do not create a session and show an error.
  • Restarting the app preserves a valid local session token.
  • Logout removes the persisted session and returns to login.
  • Windows target builds successfully.

7. Recommended Next Steps

  1. Complete Phase 2 lifecycle handling: add centralized app lifecycle state restoration and resource cleanup for backgrounding and resume.
  2. Complete Phase 3 permissions: request camera permission explicitly and handle denied, restricted, and permanently denied states.
  3. Add responsive resources: use OnIdiom and OnPlatform styles for phone, tablet, desktop, Android, iOS, and Windows differences.
  4. Add platform customization: introduce a small handler mapper example only where the native control behavior requires it.
  5. Introduce an API boundary: move credential verification and user management to a backend service.
  6. Replace the seed account: remove the packaged password and add controlled provisioning for development environments.
  7. Unify persistence: migrate work orders from sqlite-net to EF Core migrations if a single relational model is preferred.
  8. Add authorization: model technician, supervisor, and administrator permissions.
  9. Add automated tests: cover hash verification, invalid credentials, logout, inactive users, and database initialization.
  10. Add observability: structured authentication events without logging passwords or tokens.
  11. Plan offline sync: define conflict handling, local queueing, and server reconciliation for field connectivity.
